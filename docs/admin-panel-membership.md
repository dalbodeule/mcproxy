# 관리패널 다국어·회원제·UI/UX 계획

## 현재 반영 범위

관리패널은 별도 SvelteKit 3+ 서버에서 동작하며 `ko`, `en`, `ja` locale을 서버에서 결정합니다. `mcproxy_locale` cookie로 사용자가 로그인 전후 언어를 바꿀 수 있고, 번역 문자열은 `admin-panel/src/lib/i18n.ts`에서 관리합니다. 패널의 API 토큰은 계속 서버에만 보관하며 브라우저로 전달하지 않습니다.

현재는 초기 관리자 계정을 환경변수로 부트스트랩한 뒤 초대 기반으로 회원을 추가할 수 있습니다. 회원 데이터와 초대 토큰은 패널 전용 SQLite에 저장하며, 역할과 서버 범위를 서버 측에서 검사합니다. 세션의 username과 회원 ID는 membership 권한 검사와 감사 actor에 연결됩니다. 규칙 삭제 시에는 폼의 `server_id`를 신뢰하지 않고 실제 규칙의 서버 소속을 API에서 재조회하며, scoped 목록도 규칙의 `server_id` 기준으로 필터링합니다. 제한된 관리자는 자신이 가진 서버 범위의 부분집합만 회원에게 부여할 수 있고, 전체 범위(`[]`) 회원을 만들거나 관리할 수 없습니다.

패널의 서버사이드 API proxy는 검증된 세션 username을 내부 API에 전달하고, 내부 API는 토큰 인증이 성공한 경우에만 이를 감사 actor로 기록합니다. 직접 API 토큰을 사용하는 호출은 기존처럼 `admin-api` actor를 사용합니다.

## 회원제가 유용한 경우

회원제는 Minecraft 플레이어 인증이 아니라 관리패널 운영자 인증에만 사용해야 합니다. 서버 운영자가 한 명이면 현재의 단일 관리자 계정으로 충분하지만, 다음 상황에서는 회원제가 유용합니다.

- 여러 운영자가 서버별 정책과 BungeeGuard 토큰을 관리하는 경우
- 누가 정책을 바꾸거나 토큰을 회전했는지 감사해야 하는 경우
- 외부 운영 대행/고객사별로 접근 범위를 분리해야 하는 경우
- SaaS 형태로 여러 mcproxy 인스턴스를 한 패널에서 관리하는 경우

## 권장 도입 순서

### 1단계: self-hosted 팀 회원제

공개 회원가입은 만들지 않고 Owner가 초대하는 방식으로 시작합니다.

| 역할 | 권한 |
| --- | --- |
| Owner | 조직·멤버·시크릿·결제·전체 설정 |
| Admin | 서버·정책·룰·토큰 관리, 멤버 조회 |
| Operator | 서버 활성화/비활성화와 운영 상태 조정 |
| Auditor | 통계·감사로그 조회만 |
| Viewer | 읽기 전용 대시보드 |

현재 구현된 기능은 초대 만료/단회 사용, 비밀번호 최소 길이, 본인 비밀번호 변경, Owner/Admin의 임시 비밀번호 재설정, 회원 역할·서버 범위 변경, 회원 활성화/비활성화, 로그아웃·비밀번호 변경·재설정 시 세션 폐기, TOTP MFA, 활성 회원 재검증, 로그인 실패 제한, 회원 변경의 actor 기록입니다. 멤버별 `server_id` 범위는 페이지 action뿐 아니라 범용 `/api/v1/*` proxy의 경로·query·JSON body 검사와 서버 목록/감사 목록 필터에도 적용됩니다. 마지막 활성 Owner는 비활성화할 수 없습니다. WebAuthn은 하드웨어 키 수요가 확인될 때 추가합니다.

### 2단계: 조직/프로젝트 분리

SaaS 또는 여러 고객사를 지원할 때만 `organization`을 도입합니다. 서버·정책·룰·감사로그·API 토큰은 모두 `organization_id`로 격리하고, 모든 조회와 mutation에서 tenant scope를 강제해야 합니다. UI에서 숨기는 것만으로는 격리가 되지 않습니다.

권장 핵심 엔티티는 `users`, `organizations`, `memberships`, `invitations`, `sessions`, `api_tokens`, `audit_events`입니다. API 토큰은 평문 저장 대신 해시를 저장하고, secret은 기존 `*_FILE`/외부 Secret Manager 흐름을 유지합니다.

### 3단계: 기업 로그인·과금

수요가 확인된 뒤 OIDC를 먼저 추가하고, SAML/SCIM은 기업 고객 요구가 있을 때 추가합니다. 과금은 로그인 기능과 분리해 조직 단위 플랜, 관리 서버 수, 활성 사용자 수, 보존 기간을 기준으로 설계합니다. Minecraft 접속자 수를 곧바로 과금 기준으로 삼으면 공격 트래픽과 정상 사용량을 구분하기 어렵습니다.

## 권장 결론

현재 프로젝트에는 공개 회원가입이나 결제보다 `초대 기반 운영자 회원제 + RBAC + 서버별 scope + MFA + 감사로그`가 우선입니다. 단일 서버를 직접 운영하는 사용자의 배포 복잡도를 높이지 않도록 기존 단일 관리자 모드는 유지하고, 회원제는 선택 기능으로 추가하는 것이 적절합니다. SaaS 전환은 조직 격리와 비밀 관리가 검증된 뒤 별도 단계로 진행합니다.

## UI/UX 반영 현황 및 다음 작업

- 반영: 대시보드 Gate 상태·backend·cache age·차단률 카드
- 반영: Auditor는 통계·감사로그만 조회하고 회원·초대 관리 페이지에는 접근할 수 없도록 역할 경계를 고정
- 반영: 대시보드 즉시 확인 영역(Gate 미준비, Redis degraded, stale cache, 감사 저장 실패)과 정상 상태 안내
- 반영: 서버 위험 작업(삭제·토큰 회전) 확인 단계
- 반영: 모바일 정책/감사로그 세로 레이아웃과 키보드 focus/skip link
- 반영: 오류·성공 메시지의 한·영·일 다국어화와 `aria-live` 피드백
- 반영: locale별 날짜/숫자 포맷과 고대비 테마
- 다음: 실제 운영자 피드백을 기준으로 카드 순서와 경보 threshold를 배포 환경별 튜닝
